REGRA FUNDAMENTAL
==================================================

NÃO PRESUMA QUE UMA FUNCIONALIDADE ESTÁ AUSENTE.

Investigue primeiro.

Para cada requisito deste documento, classifique o sistema atual como:

EXISTING_SUPERIOR
EXISTING_EQUIVALENT
EXISTING_PARTIAL
EXISTING_INFERIOR
NOT_IMPLEMENTED
NOT_APPLICABLE
UNKNOWN

EXISTING_SUPERIOR:
nosso sistema já possui solução que você considera superior.

EXISTING_EQUIVALENT:
já existe solução equivalente.

EXISTING_PARTIAL:
parte da funcionalidade existe.

EXISTING_INFERIOR:
existe, mas há benefício objetivo em evoluí-la.

NOT_IMPLEMENTED:
não existe.

NOT_APPLICABLE:
não faz sentido para o produto.

UNKNOWN:
não foi possível concluir após investigação.

==================================================
CICLO CENTRAL DO PRODUTO
==================================================

Toda decisão de produto, arquitetura e implementação deve considerar este ciclo como o fluxo central da plataforma:

JOGAR
→ ANALISAR
→ ENTENDER O ERRO
→ RECOMENDAR TREINAMENTO
→ APRENDER
→ PRATICAR
→ RESOLVER DESAFIOS
→ MEDIR DOMÍNIO
→ JOGAR NOVAMENTE

Este ciclo NÃO é apenas conceitual.

Ele deve existir tecnicamente no produto e conectar os diferentes módulos da plataforma.

A plataforma deve ser projetada como um sistema contínuo de evolução do jogador, e não como um conjunto de telas ou funcionalidades independentes.

==================================================
1. JOGAR
==================================================

O usuário joga uma partida.

Ao finalizar, registrar os dados necessários para permitir análise posterior, respeitando a arquitetura existente.

Possíveis dados:

- movimentos;
- resultado;
- modalidade;
- controle de tempo;
- rating quando aplicável;
- duração;
- PGN;
- posição final;
- metadados relevantes;
- adversário;
- origem da partida;
- tipo da partida;
- se foi treino, casual ou competitivo.

A partida deve alimentar o restante do ciclo.

Não duplicar armazenamento se o sistema já possui histórico adequado.

==================================================
2. ANALISAR
==================================================

Após a partida, oferecer análise quando disponível.

A análise deve procurar:

- erros;
- imprecisões;
- oportunidades perdidas;
- problemas de abertura;
- padrões táticos;
- problemas estratégicos;
- problemas de final;
- decisões críticas;
- mudanças relevantes de avaliação.

Não limitar a análise a mostrar avaliação do engine.

O objetivo é produzir informação utilizável pelo sistema de aprendizagem.

==================================================
3. ENTENDER O ERRO
==================================================

Transformar erros detectados em explicações compreensíveis.

Exemplo:

NÃO apenas:

"Blunder: -3.4"

Preferir algo como:

"Este lance permitiu um garfo que atacou duas peças."

Quando tecnicamente possível, associar o erro a uma skill da taxonomia interna.

Exemplo:

mistake
→ tacticalPattern
→ fork

ou:

mistake
→ endgame
→ opposition

Criar relação conceitual:

Game
→ Analysis
→ Mistake
→ Skill

Cada erro relevante deverá, quando possível, possuir:

mistakeType
severity
skill
position
movePlayed
recommendedMove
explanation
confidence

Não inventar explicações sem base técnica suficiente.

==================================================
4. RECOMENDAR TREINAMENTO
==================================================

O RecommendationService deve consumir os resultados da análise.

Exemplo:

3 partidas recentes apresentam dificuldade em:

kingSafety

Então recomendar:

"Treinar segurança do rei"

Outro exemplo:

usuário perdeu repetidamente finais de torres.

Recomendar:

"Praticar finais de torres"

As recomendações devem possuir justificativa rastreável.

Evitar recomendações aleatórias.

Cada recomendação deverá poder registrar:

reason
source
skill
priority
createdAt
completedAt

Exemplo:

Recommendation {
 type: TRAIN_WEAKNESS,
 skill: "fork",
 reason: "3 erros relacionados nas últimas 5 partidas"
}

==================================================
5. APRENDER
==================================================

Se existir conteúdo educacional relacionado à fraqueza:

direcionar o usuário para ele.

Exemplo:

fraqueza:
backRankMate

→ aula:
Fundamentos de mate na última fileira

Após conclusão:

atualizar LearningProgress.

Não criar aulas fictícias se não houver conteúdo correspondente.

Se não houver aula adequada:

oferecer prática ou desafio relacionado.

==================================================
6. PRATICAR
==================================================

Depois da explicação teórica, oferecer prática dirigida.

Exemplo:

aula sobre oposição

→ exercícios de oposição

ou:

fraqueza em finais de torres

→ prática de finais de torres.

O Practice Engine deve utilizar SkillMastery para selecionar exercícios adequados quando houver dados suficientes.

A prática pode ser:

guiada
livre
adaptativa
revisão
reforço

==================================================
7. RESOLVER DESAFIOS
==================================================

Conectar desafios existentes à taxonomia de skills.

Exemplo:

Puzzle {
 skills: [
   "fork",
   "doubleAttack"
 ]
}

Quando o usuário resolver:

atualizar:

PuzzleRating
PuzzleProgress
SkillMastery

quando aplicável.

Não alterar desafios existentes apenas para encaixá-los artificialmente nessa arquitetura.

Temas antigos podem continuar como metadados.

==================================================
8. MEDIR DOMÍNIO
==================================================

SkillMastery deve consolidar sinais provenientes de diferentes atividades.

Possíveis fontes:

partidas
puzzles
practice
lessons
training
analysis

Exemplo conceitual:

SkillMastery {
 skill: "fork",

 puzzlePerformance: ...,
 gamePerformance: ...,
 practicePerformance: ...,
 lessonProgress: ...,

 confidence: ...,
 score: ...,
 lastUpdatedAt: ...
}

Não usar média simples sem justificativa.

A metodologia deve considerar:

- quantidade de observações;
- recência;
- dificuldade;
- contexto;
- confiabilidade da evidência.

Também deve distinguir:

"não existem dados suficientes"

de:

"o usuário possui domínio baixo".

==================================================
9. JOGAR NOVAMENTE
==================================================

Depois de treinamento relevante, incentivar o usuário a aplicar o aprendizado em partida real ou de treinamento.

Exemplo:

"Você treinou finais de torres. Agora experimente aplicar isso em uma partida."

O ciclo então reinicia:

JOGAR
→ ANALISAR
→ ENTENDER
→ RECOMENDAR
→ APRENDER
→ PRATICAR
→ RESOLVER
→ MEDIR
→ JOGAR

==================================================
CONTEXTO ENTRE MÓDULOS
==================================================

Ao navegar entre módulos, preservar o motivo da recomendação quando útil.

Exemplo:

Partida
→ erro de garfo
→ recomendação
→ treino de garfo

O módulo de treino deve saber que o usuário chegou ali por causa daquela fraqueza.

Após completar:

registrar que o treinamento foi realizado.

Isso permite posteriormente avaliar se houve melhora.

==================================================
FEEDBACK LOOP
==================================================

O sistema deve conseguir responder:

"O treinamento recomendado realmente ajudou?"

Exemplo:

ANTES:
desempenho baixo em fork.

TREINAMENTO:
12 puzzles de fork.

DEPOIS:
novas partidas apresentam melhor desempenho nessa skill.

Então:

SkillMastery aumenta.

Se não houver melhora:

RecommendationService poderá recomendar:

- treinamento adicional;
- conteúdo mais básico;
- prática diferente;
- revisão conceitual.

==================================================
HOME COMO ORQUESTRADOR
==================================================

A Home deve refletir o ciclo.

Ela não deve apenas listar funcionalidades.

Deve responder:

"Qual é a próxima ação mais útil para este jogador?"

Exemplos:

"Revisar sua última partida"

"Continuar treinamento de finais"

"Você melhorou em garfos"

"Praticar defesa"

"Continuar aula"

"Resolver problema diário"

"Jogar novamente"

A Home deve priorizar continuidade.

==================================================
PRINCÍPIO DE CONTINUIDADE
==================================================

Evitar becos sem saída.

Após uma ação importante, sempre avaliar qual próximo passo faz sentido.

Exemplos:

PARTIDA FINALIZADA
→ analisar

ANÁLISE FINALIZADA
→ treinar fraqueza

AULA FINALIZADA
→ praticar

PRÁTICA FINALIZADA
→ resolver desafios relacionados

TREINO FINALIZADO
→ jogar

PUZZLE JOURNEY
→ continuar progressão ou aplicar habilidade

Isso NÃO significa obrigar o usuário a seguir o fluxo.

São recomendações contextuais.

O usuário continua livre para navegar normalmente.
