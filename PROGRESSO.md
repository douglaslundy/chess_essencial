Causa raiz bem mais profunda que o bug de `613b052`: `DatabaseService` (`apps/api/src/database/database.service.ts`) compartilhava a MESMA conexão `postgres.Sql` entre `this.client` (tagged-template raw, usado por quase todo repositório do projeto) e `this.db` (Drizzle ORM, só usado por `users.repository.ts`) — `drizzle(client, {schema})` zera os parsers globais de `date`/`time`/`timestamp`/`timestamptz` dessa conexão como efeito colateral de embrulhá-la (confirmado lendo o próprio código-fonte do driver, `drizzle-orm/postgres-js/driver.js#construct`), fazendo toda query raw na mesma conexão devolver essas colunas como string crua em vez de `Date` — só que o bug fica invisível enquanto a coluna é `NULL` (o optional chaining mascara), só aparece quando um valor de verdade é gravado pela primeira vez. Reproduzido ao vivo dentro do próprio container de produção (scripts Node isolados, só leitura, nunca tocando dado real) antes de mexer em qualquer código — inclusive confirmando que dar ao Drizzle uma conexão `postgres()` própria resolve sem mudar mais nada. Corrigido `DatabaseService` pra abrir duas conexões (`this.client` intocado pro resto do app; conexão nova dedicada só pro Drizzle), `onApplicationShutdown` agora encerra as duas. **Bônus real da correção**: o mesmo mecanismo já valia pra `subscriptions.repository.ts#getActiveSubscriptionForUser()` (`current_period_end`, lido via `this.database.client` raw igual a `ai_provider_keys`) — só não tinha disparado ainda porque as 2 assinaturas ativas em produção têm essa coluna `NULL` (confirmado com query direta). - Causa exata: `crypto.randomUUID()` só existe em "contextos seguros" (HTTPS ou `localhost`) por especificação do navegador. A "produção" observada rodava em HTTP puro num endereço de rede local, que NÃO é um contexto seguro — então `crypto.randomUUID` simplesmente não existe nesse navegador. `GameSocket.submitMove()` (`game-socket.ts`) chamava `crypto.randomUUID()` como a primeira linha da função; a exceção síncrona interrompia a função ANTES de `this.send(...)` rodar, então nenhum lance saía do navegador e a linha seguinte em `game-room.tsx` (`setMessage('Lance enviado...')`) nunca era executada — por isso zero mensagem, zero erro visível, só a peça "não indo pro destino". `playDemoMove` em `game-room.tsx` tinha o mesmo padrão (não reportado ainda pelo usuário, mas seria o mesmo bug no tabuleiro demonstrativo). Exercícios nunca chamam `crypto.randomUUID`, por isso sempre funcionaram.
- Correção: criado `apps/web/src/lib/uuid.ts` com um `randomUUID()` que usa `crypto.randomUUID` quando disponível e cai para construir um UUID v4 manualmente via `crypto.getRandomValues` (que, ao contrário de `randomUUID`, FUNCIONA em contextos inseguros) quando não. Substituído nos dois pontos (`game-socket.ts` submitMove, `game-room.tsx` playDemoMove). Teste novo (`uuid.test.ts`) cobre os dois caminhos, inclusive simulando `crypto.randomUUID` ausente. Gates locais passaram: typecheck, lint, 26 testes web (24 + 2 novos), build de produção, Prettier. Commit `c00a330` enviado.
- Débito técnico REAL exposto por esse bug: a "produção" não tem HTTPS (só HTTP puro num IP LAN). Isso já quebrou uma feature crítica silenciosamente uma vez; qualquer outra API restrita a contexto seguro usada no futuro (ex: `crypto.subtle`, clipboard, geolocalização precisa, service workers) vai ter o mesmo tipo de falha silenciosa. Não resolvido nesta sessão (fora de escopo/exigiria certificado TLS), só registrado como risco conhecido.
